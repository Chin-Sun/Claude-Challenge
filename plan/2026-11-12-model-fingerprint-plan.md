# Claude 注水攻防挑战：实施计划 v2（吸收 GitHub 调研后修订）

> v1 位于 `~/.claude/plans/pasted-content-id-56ba-run-splendid-kite.md`，本文件取代它。
> 文中准确率、得分均为估计值，需本地模拟赛校准。

## Context

10 个匿名模型 ID，总共 100 次请求（限次不限额），截止 11-16 10:00。第一题找指定模型（对 +20，错 −10），第二题识别其余模型（名称 +10，版本 +10，错 0）。脚本、框架、模型须在本地运行。排名按"猜对多且请求次数少"。

本质是**黑盒、低预算、开放集的模型识别**，而且主办方是"防守方"，会主动伪装。

## 调研结论对计划的四处修正

1. **最接近的先例是 LLMmap**（USENIX Security 2025），其余大多数项目做的是"它是不是宣称的那个"的一对一核验，我们要做的是一对多识别。LLMmap 用约 8 个查询识别 42 个模型版本，准确率约 95%。照搬它的两点：用参考数据按信息增益**挑查询**；训练参考库时**随机套用大量不同的 system prompt 和参数**，让分类器对伪装不敏感。
2. **信号要按"能不能伪装"分级**。多个项目独立得出同一结论：基础设施信号（分词器、报错文本）不受 system prompt 影响；行为信号会被 system prompt 大幅改变（Tosea 的实测是：仅换 system prompt 带来的分布偏移，就和直接换模型一样大）。决策时按这个顺序加权：分词器/报错 > 能力 > 知识截止 > 文风 > 自我声明。
3. **"一次请求塞满探针"有风险，必须先验证**。统计类方法（单 token 分布、MMD 检验）每个模型要 100 到 400 次请求，预算不允许；把探针打包进一次请求后，答案之间会互相影响，不再是独立样本。只要参考库也按完全相同的打包方式采集，这样做仍然有效（llm-relay-verifier 就是一次请求要 150 个随机数）。但这必须在模拟赛里验证，必要时拆成 2 次请求。
4. **同家族内部，分词器只能分代，分不了档位**。分档（Haiku/Sonnet/Opus/Fable）要靠首字延迟、生成速度、高难题通过率；分代和版本靠知识截止和分词器。

## 方法组合

| 层 | 内容 | 主要作用 | 来源 |
|---|---|---|---|
| L1 基础设施 | 4 条固定文本的 token 数（英文、中文、代码、emoji），**以单字符请求为基线做差**，抵消服务端模板带来的额外 token；`finish_reason` 取值、`id` 前缀、`system_fingerprint`、`reasoning_content` 字段（OpenAI 兼容模式，见下文） | 厂商、代际 | modelprint、llm-relay-verifier |
| L2 速度 | 首字延迟、每秒 token 数 | 档位 | codex-model-watch |
| L3 能力阶梯 | 程序随机生成参数、答案可程序校验的难题（代码追踪、日历推算、骑士与无赖、中国剩余定理），提示词禁止用工具 | 档位 | ccfingerprint、llm-relay-verifier |
| L4 知识锚点 | 带日期的事件题，推断真实知识截止；检查"自称 X 的模型是否知道 X 截止前的事件" | 版本 | ccfingerprint |
| L5 行为指纹 | 打包的伪随机序列、强制单词作答、拒答措辞 | 精确型号 | LLMmap、Tosea、relay-verifier |
| L6 文体 | 一段自由写作，用本地 TF-IDF + 逻辑回归分类 | 厂商 | llm-idiosyncrasies |
| 决策 | 各层似然相乘得后验；多个 ID 疑似同一模型时合并证据；后验不够就发针对性区分卷 | 停止条件、第一题阈值（后验 > 1/3 才选） | LLMmap、llm-verify、ShadowHunter |

**按需使用、需先确认失败请求是否计数的探针**：`max_tokens` 设成极大值，读报错里的真实输出上限；`temperature` 越界，读校验报错的原文。这两类报错文本对版本的区分度很高，但被拒的请求可能照样扣次数。

**不采用**：TRAP（需要对参考模型做梯度优化，闭源 Claude 做不到）；各类统计检验（样本量需求远超预算）；panshi 的 relay-guard（把答案上传到服务端判分，违反本地运行约束）；LLM2vec 分类器（需要 24GB 显存，Mac 上用 TF-IDF 替代）。

## 验证方式

1. 模拟网关随机抽 10 个候选模型，藏在 model-a 至 model-j 后面，随机加伪装 system prompt，跑完整流程
2. 按比赛规则自动算分，重复 20 轮以上，报告平均分 ± 标准差、平均请求数、混淆矩阵
3. 单独报告"有伪装"和"无伪装"两种条件下的准确率，确认分级加权确实起作用
4. 达标线：平均分 ≥ 160 且平均请求数 ≤ 20
5. 彩排时核对计数账本与实际发出的请求数完全一致

### OpenAI 兼容模式对方法的影响

| 影响 | 处理 |
|---|---|
| 失去 Claude 原生流式事件结构和 thinking 签名的检查 | 从 L1 删除这两项 |
| `usage` 可能是网关用自己的分词器重新算的，而不是上游返回的（one-api/new-api 一类网关在部分渠道会这样做） | 第一轮先检查：10 个 ID 对同一段文本的 token 数如果完全相同，并且等于本地 tiktoken 的计数，就说明是网关重算的，分词器信号作废，权重转给能力和速度 |
| 响应里 `id` 前缀、`system_fingerprint`、`model` 回显、`reasoning_content` 字段是否存在，可能泄露上游厂商 | 加入 L1，但默认它们可能被网关改写，只作弱证据 |
| `n>1`（一次请求返回多个样本）如果被透传，一次请求就能拿到多个独立样本，单 token 分布类方法也就变得可行 | 先确认带 `n` 的请求按 1 次计数，并且不会报错。确认之前不在正式比赛中使用 |
| `logprobs` 参数各厂商支持情况不同，本身就是厂商信号 | 被拒的请求可能计数，仅在确认失败请求不计数后使用 |

- 赛前用官方 API 采集参考数据：合规
- 被拒的请求计数；网络原因导致的失败不计数

### 计数规则带来的约束

- **正式请求只用最保守的参数**：只带 `model`、`messages`、`max_tokens`（取适中值）、`temperature`（取 0 到 1 之间，各家都接受的范围）。不带 `n`、`logprobs`、`stop` 等可能被某些后端拒绝的参数
- **报错类探针默认不用**：`max_tokens` 超大、`temperature` 越界这类探针，依靠的就是"被拒"，每次都要花掉 1 次请求。只有当两个候选在其他信号上都分不开，并且报错文本恰好能区分它们时，才作为最后手段
- **客户端重试规则**：只在明确的网络层失败时重试（连接被拒、DNS 失败、TLS 握手失败，这些情况下请求根本没到服务器）。收到任何 HTTP 响应，包括 4xx 和 5xx，一律不重试，记入账本。读超时也不重试，因为请求可能已被处理并计数；超时时间设长（如 600 秒），用流式接收避免长回复触发超时
- **探针卷要在本地模拟网关上预先跑通**，确保不会因为格式问题被拒

## 不采用：FlashProve（Anthropic，2026-10）

FlashProve 是推理过程的零知识证明，需要服务方配合：服务方先承诺权重，再为每次回复生成证明。目前只支持 Llama 4 Maverick（整数量化、贪心解码），证明端需要 H100，验证端只支持 Linux。本赛题的服务方就是对手，不会生成证明，所以用不上。可借鉴的一点：论文指出浮点推理在不同机器上无法逐位复现，所以参考指纹要按分布比对，不能要求逐字一致，即使 temperature=0 也一样。
