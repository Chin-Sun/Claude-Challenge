## 1. 项目是什么

**"注水"**指 API 中转商挂着高端模型的名字（如 Opus 5.5），实际返回的是便宜模型（低档 Claude、旧版 Claude，或完全不是 Claude 的模型）。**"攻防"**是主办方负责伪装（防），参赛者负责识破（攻）。

本质是一道**黑盒模型指纹识别**题：

| 要素 | 内容 | 对策略的含义 |
|---|---|---|
| 输入 | 10 个匿名模型 ID | 平均每个模型只有 10 次请求 |
| 预算 | 总共 100 次请求，**限次不限额** | 单次请求的 token 不受限，所以每次请求要塞满探针、要长输出 |
| 第一题（多选） | 找出指定模型：对 +20，错 −10，不选 0 | 有惩罚。后验概率 > 1/3 才值得选（20p − 10(1−p) > 0） |
| 第二题（填空） | 其余模型：名称 +10，版本 +10，错 0 | 无惩罚，**任何情况下都要填最可能的猜测**，名称和版本分开拿分 |
| 排名 | 猜对多，且请求次数少 | 准确率优先，请求数是第二目标，要做"够用即停" |
| 约束 | 脚本、框架、模型都在本地运行 | 分类器和判分模型不能用云端 LLM，只能本地算 |

**要做的东西**：一套本地工具，用尽量少的请求向每个匿名 ID 发精心设计的探针，把响应和事先建好的"已知模型指纹库"比对，输出每个 ID 的模型判断和置信度。

**需要向主办方确认的点**（不影响开工，影响细节）：
- "model-a ～ model-k"是 11 个字母，题面写 10 个，数量待确认
- 接口协议是 Anthropic 原生还是 OpenAI 兼容；能否自带 system prompt、调 temperature、开流式
- 失败或报错的请求是否计入次数
- 指定模型在 10 个里可能有多个（题型是多选）
- 赛前用官方 API 采集参考指纹是否符合"本地运行"的要求（我理解约束的是计算和判分，待确认）

## 2. 方法清单与选择理由

按"每次请求能拿到的信息量"从高到低排列。

### 方法 A：协议与元数据侧信道（每次请求免费附带）

不需要额外请求，从每个响应里顺手提取：
- **分词器指纹**：让模型原样复述一段固定文本，读 `usage.output_tokens`。不同厂商、不同代的分词器对同一段文本给出的 token 数不同，这是接近确定性的信号
- 响应结构：`id` 前缀格式、`stop_reason` 取值、`model` 字段、响应头
- 速度：流式下的首字延迟和每秒 token 数，不同档位差别明显
- thinking 块及其签名是否存在（Anthropic 原生协议下）

**为什么选**：零成本，且分词器这类信号是模型很难伪装的。**弱点**：主办方网关如果统一改写了元数据，这部分直接失效，所以只能当加分项，不能当主力。

### 方法 B：单请求"超级探针卷"（主力）

利用"不限额"，把 40 到 60 个子探针合进**一次请求**，要求按固定 JSON 结构作答：

| 探针类别 | 区分什么 | 例子 |
|---|---|---|
| 知识截止 | 版本和代际 | 列出 2024 至 2026 年按月分布的事件，问知道哪些 |
| 能力阶梯 | 档位（Haiku / Sonnet / Opus / Fable 级） | 一组难度递增的推理、数学、代码题 |
| 强制短答 | 模型身份 | 40 道"只答一个词"的题，得到答案向量 |
| 伪随机偏好 | 模型身份 | "随机给 30 个数字 / 词"，各模型的偏好分布不同 |
| 自由写作 | 文风 | 中英文各一段 500 字短文，供文体分类器用 |
| 自我认知 | 厂商（弱信号） | 多语言、多角度问身份，套壳模型常在侧面问法下露底 |
| 特殊字符串处理 | 厂商 | 复述各家的特殊 token，不同家族的处理方式不同 |
| 拒答风格 | 厂商和代际 | 几道边界请求，看拒绝的措辞和尺度 |

**为什么选**：这是和"限次不限额"最匹配的设计，一次请求拿到几十个相互独立的证据。同一份卷子发给全部 10 个 ID，还能横向聚类，发现哪几个 ID 背后是同一个模型。

### 方法 C：参考指纹库 + 贝叶斯序贯决策（决策核心）

- 赛前把同一份探针卷发给所有候选真模型，每个模型跑 5 到 10 次，得到每个探针的答案分布
- 比赛时对每个匿名 ID 计算"它是候选 X"的后验概率
- 后验够高就停，不够就从预先备好的"区分卷"里挑一份最能分开前两名候选的再发一次

**为什么选**：直接对应评分规则。后验概率可以套用 1/3 的选择阈值，也让"请求数最少"有了客观的停止条件，不靠感觉决定要不要多问一次。

### 方法 D：本地文体分类器（方法 B 的自由写作部分的判分器）

字符 n-gram TF-IDF 加逻辑回归，可选加一个本地嵌入模型（如 bge-m3）。全部在本机跑。

**为什么选**：已有研究表明仅凭文本就能高准确率区分不同厂商的模型，而且文风比自我认知难伪装。满足"模型必须本地运行"。**弱点**：同一家族相邻档位的文风很像，分版本的能力有限。

### 方法 E：针对性区分卷（第二轮，按需）

为易混淆的候选对各准备一份专用卷，如 Opus 5.5 对 Fable 5.2、Sonnet 5.5 对 Opus 5.5、新旧两代同档位。内容偏向更难的能力题和更细的知识截止题。

**为什么选**：第一轮通常能定厂商和大致档位，剩下的不确定性集中在少数几对上，专用卷的单次信息量远高于再发一次通用卷。

### 方法 F：参数与上下文窗口探测（备用，有风险）

发超长上下文或特定参数，看是否被接受。结果接近确定性，但**被拒绝的请求可能照样计数**，所以只在失败请求不计数，或其他方法都分不开时使用。

### 不推荐的做法

| 做法 | 不选的原因 |
|---|---|
| 只问"你是什么模型" | 一句 system prompt 就能伪装，这正是主办方最先做的防御 |
| 每个模型发很多短请求做统计 | 浪费次数，和"限次不限额"相反 |
| 用云端 LLM 当裁判 | 违反本地运行约束 |
| 依赖 logprobs | Claude 接口不提供，覆盖面太窄 |

## 3. 各方法预期结果与评分契合度

以下为估计值，待模拟赛校准。

| 方法 | 额外请求数 | 厂商/名称准确率 | 精确版本准确率 | 与评分的契合度 |
|---|---|---|---|---|
| A 元数据侧信道 | 0 | 网关透传时接近 100%，被改写时为 0 | 透传时较高 | 高：不花次数。但不可依赖 |
| B 超级探针卷 + C 贝叶斯 | 每模型 1 | 约 95% | 约 70% 至 85% | 最高：信息密度和请求数同时最优 |
| D 文体分类器单独用 | 0（复用 B 的输出） | 约 90% | 约 60% 至 75% | 中高：稳拿名称分，版本分不稳 |
| E 区分卷（叠加在 B+C 上） | 每个存疑模型 1 至 2 | 约 97% | 约 85% 至 95% | 高：花少量次数换版本分和第一题的把握 |
| F 参数/上下文探测 | 每次 1，可能白费 | 视情况 | 特定模型对上接近确定 | 中：收益确定但有浪费次数的风险 |
| 只问自我认知 | 每模型 1 | 约 30% 至 50% | 低 | 低：正好撞在防御上 |

**推荐组合 A + B + C + D，按需加 E**，预期：
- 总请求数 **12 至 20 次**（第一轮 10 次，第二轮 2 至 10 次），远低于 100 的上限
- 满分 200（10 个模型各 20 分）的情况下，预期 **150 至 185 分**
- 主要失分点：同家族相邻版本混淆，以及主办方对输出做了重度后处理的情况

**停止阈值的取舍**：一次误判损失 20 到 30 分，而请求数只是第二排序指标，所以我建议宁可多发几次区分卷，也不要为了省次数带着 60% 的把握交卷。阈值做成可配置，模拟赛后再定。

## 4. 实施计划

### 目录结构（全部新建于 `/Users/sunqian/Desktop/Projects/Competitions/ClaudeChallenge/`）

```
client/        请求客户端：关闭自动重试、流式落盘、记录原始响应/响应头/计时，
               带持久化的请求计数账本和硬上限
probes/        battery_v1（第一轮通用卷）、discriminators/（各混淆对的区分卷）
reference/     采集脚本与各候选模型的参考响应
features/      从响应提取特征：答案向量、token 数、速度、文体特征
classify/      贝叶斯后验计算、文体分类器、停止与选卷逻辑
sim/           本地模拟网关（把真模型藏在匿名 ID 后，可加伪装）与评估脚本
run_contest.py 比赛当天的入口
```

### 时间安排

| 时间 | 工作 |
|---|---|
| 11-12 | 客户端和计数账本；写第一轮探针卷；确定候选模型清单 |
| 11-13 | 采集参考指纹（Claude 各档各代，加国内外主流非 Claude 模型，版本以各家当前官方模型列表为准）；每个模型同时采"裸跑"和"带伪装 system prompt"两种 |
| 11-14 | 特征提取、贝叶斯分类、文体分类器；搭模拟网关 |
| 11-15 | 模拟赛多轮：测准确率随请求数的曲线，定停止阈值；根据混淆矩阵写区分卷；全流程彩排 |
| 11-16 早 | 指定模型揭晓后正式跑，出答案和置信度表 |

### 关键工程细节

- **每次请求都不可重来**：SDK 自动重试必须关掉（重试可能偷偷消耗次数），超时设长，流式边收边写盘，原始响应全量保存
- **先确认再开火**：正式第一发之前，先弄清失败请求是否计数、接口支持哪些参数
- **伪装鲁棒性**：参考库里包含"被 system prompt 要求自称 Opus 5.5"的样本，让分类器学会忽略自我认知、依赖难伪装的信号
- **参考采集需要的资源**：各候选模型的官方 API 密钥或聚合平台密钥，这是唯一的外部依赖，需要你们小组准备

### 验证方式

1. 模拟网关随机抽 10 个真模型藏在 model-a 至 model-j 后面，随机加伪装，跑完整流程
2. 按比赛规则自动算分，重复 20 轮以上，报告得分的均值和标准差、平均请求数、混淆矩阵
3. 达标线：模拟赛平均分 ≥ 160 且平均请求数 ≤ 20，否则回头补探针或区分卷
4. 彩排时核对计数账本和实际发出的请求数完全一致
