# Claude 注水攻防挑战：方法论筛选（按"猜对多且请求次数最少"）

> 基于 `plan/` 下已有的三份计划（v1、v2、v3）整理，不取代它们。
> 文中准确率和得分都沿用 v1 的估计值，没有实测过。项目目前只有计划，没有任何代码。

## Context

材料来源：`plan/` 下三份计划（v1、v2、v3）和本项目的三段历史对话（建立 plan 规则、v1 到 v3 的讨论与 GitHub 调研、一段只切换了模型的空会话）。

三份计划讲的其实是同一条路线的三次修订，没有互相竞争的方案。所以这份文件做的事是：把里面出现过的做法拆开，按评判标准重新归成几套可以直接比较的方案，并给出取舍。

**对评判标准的理解**：先比猜对数量，再比请求次数。强队的正确数很可能打平（只有 10 个模型，分数是离散的），所以请求次数是实际的决胜项。这是我的解读，主办方没有说明两者如何折算。

## 已确认的规则

| 项目 | 内容 |
|---|---|
| 规模 | 10 个匿名 ID，共 100 次请求，限次不限额 |
| 接口 | OpenAI 兼容（`/v1/chat/completions`） |
| 计数 | 被拒的请求计数；网络原因失败不计数 |
| 第一题 | 找指定模型：对 +20，错 −10，不选 0。后验 > 1/3 才选 |
| 第二题 | 其余模型：名称 +10，版本 +10，错 0。无惩罚，一律填最可能的答案 |
| 其他 | 计算和判分全部在本地；赛前用官方 API 采集参考数据合规 |

## 入选的三套方案

三套方案共用同一套代码（客户端、探针卷、参考库、贝叶斯分类器），区别只在"每个 ID 发几次、什么时候停"。所以只需要实现一次，用模拟赛决定最终用哪一档。

| | 方案一：单发打包 | 方案二：两段序贯（推荐） | 方案三：拆分两发加序贯 |
|---|---|---|---|
| 做法 | 每个 ID 只发 1 次打包探针卷，直接出答案 | 第一轮每个 ID 发 1 次打包卷；后验不够的 ID 再发针对性区分卷，够了就停 | 第一轮把探针卷拆成 2 次发，其余同方案二 |
| 请求数 | 10 | 12 至 20 | 20 至 30 |
| 名称准确率（估计） | 约 95% | 约 97% | 与方案二相近或略高 |
| 版本准确率（估计） | 约 70% 至 85% | 约 85% 至 95% | 与方案二相近或略高 |
| 主要风险 | 同家族相邻版本分不开；打包后答案互相干扰 | 区分卷要提前按混淆对写好 | 请求数多出一倍 |
| 什么时候选 | 模拟赛里第一轮后验已普遍很高 | 默认 | 模拟赛证明打包明显损失准确率 |

**推荐方案二。** 理由：正确数优先，一次误判丢 10 到 30 分，而多发的几次请求只影响次要排序；它的停止条件是后验概率，不靠感觉，请求数会自动压到够用为止。方案一是它在"第一轮就停"时的特例，方案三是它的退路。

### 共用的实现形式

- **探针卷（一次请求，要求按固定 JSON 作答）**：能力阶梯题（程序随机生成、答案可程序校验）、带日期的知识锚点题、伪随机序列、强制单词作答、拒答措辞、一段自由写作。
- **免费附带的信号**：`usage` 的 token 数、首字延迟、每秒 token 数、`finish_reason`、`id` 前缀等响应字段。
- **信号加权顺序**：分词器 > 能力 > 知识截止 > 文风 > 自我声明。越难被 system prompt 改变的权重越高。
- **参考库**：每个候选模型用同一份探针卷、至少 20 种 system prompt 和参数配置采集，其中包含"自称指定模型"的伪装配置。
- **决策**：各层似然相乘得后验；疑似同一模型的多个 ID 合并证据；第一题按 1/3 阈值，第二题永远填最高后验。
- **客户端**：流式落盘，持久化计数账本，硬上限 100。只在请求确定没到服务器时重试，收到任何 HTTP 响应或读超时都不重试。只带 `model`、`messages`、`max_tokens`、`temperature`、`stream`。
- **目录**：沿用 v3 的 `client/`、`probes/`、`reference/`、`features/`、`classify/`、`sim/`、`run_contest.py`。

## 淘汰的做法

| 做法 | 淘汰原因 |
|---|---|
| LLMmap 原样照搬（每模型约 8 个独立查询） | 准确率有论文支撑，但要 80 次请求，次要指标垫底。只借用它的两点：按信息增益挑探针、参考库随机套用多种配置 |
| 统计分布检验（单 token 分布、MMD） | 每个模型要 100 到 400 次请求 |
| 报错类探针（`max_tokens` 超大、`temperature` 越界） | 被拒也计数，每用一次白扣 1 次。只留作两个候选实在分不开时的最后手段 |
| `n>1` 一次取多个样本 | Claude 的兼容接口很可能不支持（未核实官方文档），被拒就白扣 |
| 只问"你是什么模型" | 一句 system prompt 就能伪装 |
| TRAP、FlashProve、relay-guard、LLM2vec | 分别需要梯度、需要服务方配合、违反本地运行、需要 24GB 显存 |

## 整理时发现的三个问题

1. **v3 的分词器探针和"每模型 1 次请求"冲突。** v3 写的是 4 条固定文本各读一次 `prompt_tokens`，再减去单字符基线，照这样做每个模型要 5 次请求，10 个模型就是 50 次。改法：直接用打包卷本身的 `prompt_tokens` 作指纹，卷子写长、混合中英文、代码和 emoji，让不同分词器的差异远大于网关隐藏 system prompt 带来的偏移；发了第二轮的 ID，再用两次请求的差值抵消这个偏移。这是我的设计，需要在模拟赛里验证它对同家族不同代是否还分得开。
2. **速度信号只能看相对排序。** 参考库走官方 API，比赛走主办方网关，绝对延迟不可比。用 10 个 ID 之间的快慢排序，权重放低。
3. **候选模型清单还没定。** 三份计划都把它列为第一天的工作，但没有产出。它决定参考库的采集范围，是当前最紧的前置项。

## 验证方式

1. 模拟网关随机抽 10 个候选模型藏在匿名 ID 后，随机加伪装，三套方案各跑 20 轮以上。
2. 按比赛规则自动算分，报告每套方案的平均分、标准差、平均请求数和混淆矩阵。
3. 选型规则：先取平均正确数最高的方案；差距在一个标准差以内时，取请求数少的。
4. 分别报告有无伪装、usage 透传或重算四种条件下的结果。
5. 彩排时核对账本与实际请求数一致，并人为制造网络错误，确认重试不会多扣次数。
